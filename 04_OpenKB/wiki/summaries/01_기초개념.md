# Summary: LightRAG Basic Concepts

This document explains the foundational idea behind [[concepts/rag]] and how [[concepts/lightrag]] extends it with a knowledge graph. In standard RAG, documents are split into chunks, embedded, retrieved by similarity, and passed to an LLM for generation. While simple and effective, this approach can miss entity relationships and broader document structure.

## Core idea

LightRAG goes beyond chunk-only indexing by extracting:

- **Text chunks** — source evidence from the original document
- **Entities** — people, organizations, concepts, places, events, and other nodes
- **Relationships** — connections between entities, with descriptions and weights
- **Vector DB** — embedding-based search over chunks, entities, and relationships
- **Graph DB** — traversal over entity-relationship structure
- **KV Store** — storage for documents, chunks, and LLM cache
- **Doc Status Store** — tracking document ingestion state

This combines [[concepts/vector-search]] with [[concepts/knowledge-graph]] style retrieval to support richer context and better global reasoning.

## Indexing workflow

LightRAG indexing is deeper than traditional RAG:

1. Split the document into chunks.
2. Use an LLM to extract entities and relationships from each chunk.
3. Merge and summarize duplicate entities/relations.
4. Embed chunks, entities, and relationships.
5. Store them in vector and graph backends.
6. Save document status and LLM cache.

A key operational point is that indexing is LLM-intensive, so cost and latency matter. The document notes that enabling **entity extraction cache** is useful in testing to reduce repeated experiment costs.

## Query modes

LightRAG provides several retrieval modes, each suited to different query types:

- **`naive`** — basic vector search for simple fact lookup
- **`local`** — searches around a specific entity for local context
- **`global`** — focuses on relationships and global structure
- **`hybrid`** — combines local and global retrieval
- **`mix`** — integrates graph and vector search; recommended when using a reranker
- **`bypass`** — skips retrieval and calls the LLM directly

The document highlights `mix` as a strong practical default when reranking is involved.

## Where LightRAG is useful

LightRAG is especially helpful for questions that require:

- connecting concepts scattered across multiple documents
- understanding the context around a specific entity
- summarizing the theme, pattern, or flow of a whole corpus
- surfacing evidence chunks alongside answers
- building an internal knowledge base with graph visualization

## Limitations and cautions

The document also emphasizes several tradeoffs:

- indexing is heavier than basic vector RAG because of additional LLM calls
- smaller LLMs may extract entities and relations poorly
- embedding model choice and dimensionality should be planned early
- changing storage backends after ingestion is not fully supported by official migration paths
- bad or duplicate entity extraction may require manual merging or cleanup

## Takeaway

LightRAG is presented as a graph-enhanced retrieval architecture that improves over basic RAG when questions depend on entity relationships, corpus-wide structure, and traceable evidence. It is more powerful than plain chunk retrieval, but also more expensive and operationally complex.
