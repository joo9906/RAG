# Summary: Advanced Features and Practical Tips

This document covers advanced LightRAG capabilities and operational guidance for real-world use. It focuses on improving retrieval quality, handling multimodal content, tracking cost, exporting knowledge graph data, managing cache, adding observability, evaluating RAG quality, and applying practical deployment tips.

## Key topics

### Reranker
- LightRAG supports reranking of retrieved chunks with a more precise relevance model.
- The official guidance recommends using reranker with `mix` mode for better query quality.
- Supported providers include Cohere/vLLM-compatible rerank APIs, Jina AI, and Aliyun.
- Reranking can be enabled by default with `RERANK_BY_DEFAULT=True`, or disabled per query.
- This is a major optimization for [[concepts/retrieval-quality]] and [[concepts/rag-configuration]].

### Multimodal integration with RAG-Anything
- LightRAG can integrate with `RAG-Anything` to handle PDFs, Office files, images, tables, and equations.
- It supports multimodal processors and a multimodal knowledge graph.
- The workflow is to connect an existing LightRAG instance to `RAGAnything`.
- This extends the system toward [[concepts/multimodal-rag]] and [[concepts/knowledge-graph]].

### Token usage tracking
- `TokenTracker` can be attached to monitor LLM usage and estimate cost.
- Cache hits do not necessarily increase token usage because they may avoid provider calls.
- Useful for measuring [[concepts/llm-usage-tracking]] and controlling operating cost.

### Knowledge graph export
- The knowledge graph can be exported to CSV, Excel, Markdown, or text.
- Vector data can also be included in exports.
- This supports backup, analysis, and external inspection of [[concepts/knowledge-graph]].

### Cache management
- LightRAG provides APIs to clear all LLM cache, either asynchronously or synchronously.
- Query-specific cache cleanup can be done using the official cache-cleaning tool.
- Cache policy is relevant to [[concepts/caching]] and performance tuning.

### Langfuse observability
- Observability support is available through the `lightrag-hku[observability]` extra.
- Langfuse environment variables are required for trace collection.
- The document notes that support is centered on OpenAI-compatible calls and may not fully cover other providers yet.
- This connects to [[concepts/observability]] and [[concepts/llm-integrations]].

### RAGAS evaluation
- LightRAG provides RAGAS-based evaluation scripts.
- Returning references and chunk content makes it easier to inspect context precision and related metrics.
- This section emphasizes evaluation workflows for [[concepts/rag-evaluation]].

## Practical quality tips

1. Separate the user query from output instructions.
   - Keep the retrieval question clean.
   - Put formatting or style instructions into `user_prompt`.

2. Start with a small corpus.
   - Check indexing quality before scaling up.
   - Adjust entity splitting, language, prompts, and model quality if needed.

3. Choose embeddings carefully from the beginning.
   - Embedding dimension affects storage schema.
   - Changing embeddings later may require reindexing.

4. Test reranker in production-like conditions.
   - The `mix` mode plus reranker combination may improve precision.

5. Split large documents before ingestion.
   - Smaller units reduce reprocessing cost and make incremental updates easier.

6. Include source file paths.
   - Improves citation quality and traceability.

7. Plan storage and workspace strategy early.
   - Storage changes are not trivial once deployed.
   - Workspace policy should be defined per team, customer, or project.

These recommendations support robust [[concepts/rag-configuration]], [[concepts/document-ingestion]], and [[concepts/troubleshooting]].

## Troubleshooting overview

The document ends with a compact troubleshooting table covering common issues:
- Initialization errors: verify `initialize_storages()` was called.
- Poor query results: inspect mode, reranker, top-k settings, and prompt separation.
- Embedding errors: check whether model or dimension changed.
- Slow indexing: review LLM performance, concurrency, and cache.
- Upload failures: check upload limits, timeouts, and proxy configuration.
- Open WebUI integration problems: verify endpoint compatibility, model naming, and prefixes.
- External exposure/security issues: ensure API key and JWT authentication are configured and whitelists are correct.

## Recommended learning path

The document suggests a practical progression:
1. Understand the core structure from `01_기초개념.md`.
2. Run the local server using `02_설치와_빠른시작.md`.
3. Upload documents and inspect graphs in WebUI.
4. Compare `/query` modes such as `naive`, `local`, `global`, `hybrid`, and `mix`.
5. Experiment with Python integration in `03_Core_API_활용.md`.
6. Add reranker and storage backend choices for production use.

## Overall takeaway

This chapter is a field guide for moving LightRAG from basic setup to a production-ready system. It highlights how reranking, multimodal ingestion, observability, evaluation, and careful operational design combine to improve retrieval quality, maintainability, and debugging capability.
