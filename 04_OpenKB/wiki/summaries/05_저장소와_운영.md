# Summary: 05. 저장소와 운영

This document explains how LightRAG organizes persistence, how to choose and configure storage backends, and what to consider when operating the system in production.

## Core idea

LightRAG separates persistence into four storage categories:

- **KV Storage**: stores LLM cache, text chunks, and document metadata
- **Vector Storage**: stores chunk/entity/relation embeddings
- **Graph Storage**: stores the entity-relation graph
- **Doc Status Storage**: tracks document processing state

This layered design makes it possible to mix local development defaults with external production-grade services as needed.

## Default storage setup

The default implementation is local and file-based:

- `JsonKVStorage`
- `NanoVectorDBStorage`
- `NetworkXStorage`
- `JsonDocStatusStorage`

These defaults are suitable for fast experiments, but production use should consider scale, concurrency, and persistence requirements.

## Supported backend choices

The document lists supported implementations for each category, including:

- **KV**: JSON, PostgreSQL, Redis, MongoDB, OpenSearch
- **Vector**: NanoVectorDB, PGVector, Milvus, Chroma, Faiss, MongoDB, Qdrant, OpenSearch
- **Graph**: NetworkX, Neo4j, PostgreSQL/AGE, Memgraph, OpenSearch
- **Doc Status**: JSON, PostgreSQL, MongoDB, OpenSearch

This shows that LightRAG can be deployed with either lightweight local storage or more scalable external systems.

## Configuration patterns

Storage can be selected in two ways:

1. **Server configuration via `.env`**
2. **Core Python initialization arguments**

Example server settings use variables such as:

- `LIGHTRAG_KV_STORAGE`
- `LIGHTRAG_VECTOR_STORAGE`
- `LIGHTRAG_GRAPH_STORAGE`
- `LIGHTRAG_DOC_STATUS_STORAGE`

The core API allows the same choices directly in the `LightRAG(...)` constructor.

A key operational warning is that changing storage implementations after documents have already been ingested is not fully supported, so backend decisions should be made early.

## Workspace isolation

A **workspace** is a logical namespace used to separate data across multiple LightRAG instances.

Isolation differs by backend:

- local stores use workspace subdirectories
- Redis, Milvus, Mongo, and PostgreSQL-backed graph/storage often use collection/table prefixes
- Qdrant uses payload-based multitenancy
- PostgreSQL-based stores use a `workspace` field
- Neo4j and Memgraph use labels
- OpenSearch uses index-name prefixes

This is a useful [[concepts/workspace isolation|workspace isolation]] pattern for multi-tenant or multi-project deployments.

## Recommended production backends

The document highlights a few practical choices:

- **Neo4j** for graph storage in production, especially when graph performance matters
- **PostgreSQL** as an all-in-one option for KV, vector, doc status, and graph storage, with Apache AGE possibly required for graph support
- **Milvus** and **Qdrant** for larger-scale vector storage
- **Faiss** for simple local vector indexing
- **OpenSearch** as a unified backend capable of handling all four storage categories

These recommendations connect to broader [[concepts/storage backend selection|storage backend selection]] and [[concepts/vector storage]] considerations.

## Concurrency and throughput

Indexing performance is described as being mainly limited by LLM throughput rather than storage alone.

Important knobs include:

- `WORKERS`: server worker count
- `MAX_PARALLEL_INSERT`: number of files processed concurrently
- `MAX_ASYNC`: total concurrent LLM requests

The document advises starting `MAX_PARALLEL_INSERT` conservatively, around 2–10, because higher parallelism can increase entity merge conflicts.

This is relevant to [[concepts/concurrency tuning]] and [[concepts/indexing performance]].

## Operational checklist

Before running LightRAG in production, the document recommends:

- finalize the embedding model and its dimension before indexing
- choose and lock in the storage backend early
- configure API keys and JWT authentication if exposed externally
- verify upload limits, proxy streaming, and timeout settings
- avoid workspace name collisions
- decide whether indexing cache should be used
- prepare cost tracking and log retention for LLM usage
- back up before mass deletion or re-indexing

## Overall takeaway

This document is a deployment-oriented guide to LightRAG persistence. It emphasizes that storage architecture, workspace isolation, and concurrency settings should be planned together, because they affect scalability, correctness, and operational safety.
