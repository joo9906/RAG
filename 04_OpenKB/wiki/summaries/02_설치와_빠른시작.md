# Summary: 02. 설치와 빠른 시작

This document explains how to install LightRAG, configure the required environment before first launch, and start either the server or the core library quickly.

## Main installation options

LightRAG can be started in three main ways:

- **PyPI installation** — best for quickly trying the server or core features
- **Source installation** — best for development, customization, and latest code
- **Docker Compose** — best for running server, WebUI, and storage together

The official documentation recommends using `uv`, though `pip` is also supported.

## Server vs. core installation

For the full server experience, including WebUI and API access, install LightRAG with the `api` extra:

```bash
uv tool install "lightrag-hku[api]"
```

With `pip`:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install "lightrag-hku[api]"
```

For direct Python usage of the `LightRAG` class, only the core package is needed:

```bash
uv pip install lightrag-hku
```

or

```bash
pip install lightrag-hku
```

## Source and Docker-based setup

Source installation is done by cloning the repository and using the project build flow:

```bash
git clone https://github.com/HKUDS/LightRAG.git
cd LightRAG
make dev
```

A more manual setup path is also shown, including syncing dependencies and building the WebUI with Bun.

Docker Compose is the simplest full-stack execution path:

```bash
git clone https://github.com/HKUDS/LightRAG.git
cd LightRAG
copy env.example .env
docker compose up
```

A key warning is that `.env` must be configured correctly before startup, especially for LLM and embedding settings.

## Required first-run configuration

Before using LightRAG, several configuration items must be set:

- LLM provider and model
- embedding provider and model
- embedding dimension
- optional reranker
- storage backend selection

This makes the document especially relevant to [[concepts/model-configuration]], [[concepts/embeddings]], and [[concepts/storage-backends]].

### Example environment configurations

The document provides two example `.env` setups:

1. **OpenAI LLM + Ollama embedding**
2. **Ollama LLM + Ollama embedding**

These examples illustrate how LightRAG can combine different providers for generation and embedding, including the need to match `EMBEDDING_DIM` with the chosen embedding model.

## Setup Wizard

If editing `.env` manually is inconvenient in source installs, LightRAG provides a wizard-like set of commands:

- `make env-base` — LLM, embedding, reranker settings
- `make env-storage` — storage backends such as PostgreSQL, Neo4j, Redis, Milvus, and Qdrant
- `make env-server` — ports, authentication, API keys, SSL
- `make env-security-check` — deployment security validation

This suggests a structured setup flow that separates model, storage, server, and security concerns.

## Starting the server

After configuration, the server starts with:

```bash
lightrag-server
```

The default port is `9621`, and the document points to:

- Swagger UI: `http://localhost:9621/docs`
- ReDoc: `http://localhost:9621/redoc`

## Quick core demo flow

For a fast Core demonstration, the document shows a minimal sequence:

- set the API key
- download sample text
- run the example script

This is useful for validating a working environment before building a larger application.

## Model selection guidance

The document includes practical recommendations for choosing models:

- LLMs of **32B or larger** are recommended
- context length should be at least **32K**, ideally **64K**
- avoid reasoning models during indexing
- stronger models can improve answer quality at query time
- recommended embedding models include `BAAI/bge-m3` and `text-embedding-3-large`
- reranker candidates include `BAAI/bge-reranker-v2-m3` and Jina models

This connects closely to [[concepts/model-selection]], [[concepts/reranking]], and [[concepts/context-window]].

## Important caution

A critical warning is that changing the embedding model, embedding dimension, or asymmetric embedding settings may invalidate existing vector data. In that case, the workspace or vector store must be cleared and documents re-indexed.

This makes compatibility between embeddings and stored vectors a major operational concern for [[concepts/vector-store-compatibility]].

## Key takeaways

- LightRAG supports multiple installation paths depending on use case.
- Server use requires the `api` extra; core usage does not.
- First-run setup is mostly about aligning LLM, embedding, storage, and reranker settings.
- The setup wizard reduces configuration friction for source installs.
- Model and embedding compatibility must be preserved to avoid reindexing issues.
