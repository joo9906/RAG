# 01. LightRAG 기초 개념

## RAG 기본 개념

RAG는 Retrieval-Augmented Generation의 약자다. LLM이 답변을 만들기 전에 외부 문서에서 관련 정보를 검색하고, 검색된 내용을 컨텍스트로 넣어 답변을 생성한다.

일반적인 RAG 흐름은 다음과 같다.

1. 문서를 작은 chunk로 나눈다.
2. 각 chunk를 embedding vector로 변환한다.
3. 사용자의 질문도 embedding vector로 변환한다.
4. 벡터 유사도로 관련 chunk를 찾는다.
5. 찾은 chunk를 LLM 프롬프트에 넣고 답변을 생성한다.

이 방식은 구현이 단순하지만, 문서 안의 엔티티 관계나 전역 구조를 잘 활용하지 못하는 한계가 있다.

## LightRAG의 핵심 아이디어

LightRAG는 문서를 chunk로만 저장하지 않는다. 문서에서 엔티티와 관계를 추출해 지식 그래프를 구성하고, 이를 벡터 검색과 함께 사용한다.

핵심 구성은 다음과 같다.

| 구성 | 역할 |
|---|---|
| Text chunks | 원문 조각. 실제 근거 텍스트 |
| Entities | 사람, 조직, 개념, 장소, 이벤트 등 문서에서 추출된 노드 |
| Relationships | 엔티티 사이의 연결, 설명, 키워드, 가중치 |
| Vector DB | chunk, entity, relationship의 embedding 검색 |
| Graph DB | 엔티티-관계 그래프 탐색 |
| KV Store | 문서, chunk, LLM cache 등 보관 |
| Doc Status Store | 문서 처리 상태 추적 |

## 인덱싱 흐름

LightRAG의 인덱싱은 일반 RAG보다 한 단계 더 깊다.

1. 문서를 chunk로 분할한다.
2. 각 chunk에서 LLM이 엔티티와 관계를 추출한다.
3. 같은 엔티티나 관계를 병합하고 요약한다.
4. chunk, entity, relationship을 embedding한다.
5. 벡터 저장소와 그래프 저장소에 저장한다.
6. 문서 처리 상태와 LLM cache를 저장한다.

이 과정에서 LLM 호출이 많이 일어나므로 비용과 속도를 고려해야 한다. 테스트 환경에서는 entity extraction cache를 켜두면 반복 실험 비용을 줄일 수 있다.

## 질의 모드

LightRAG는 여러 query mode를 제공한다.

| mode | 의미 | 적합한 질문 |
|---|---|---|
| `naive` | 기본 벡터 검색 중심 | 단순 사실 검색 |
| `local` | 특정 엔티티 주변의 지역 정보 검색 | 특정 대상의 속성, 세부 정보 |
| `global` | 관계와 전역 구조 중심 검색 | 전체 주제, 큰 흐름, 관계망 |
| `hybrid` | local + global 조합 | 폭넓은 문맥이 필요한 질문 |
| `mix` | 지식 그래프와 벡터 검색을 통합 | reranker 사용, 실전 기본값 후보 |
| `bypass` | RAG 검색 없이 LLM 직접 호출 | 일반 채팅 또는 비교 테스트 |

공식 문서에서는 reranker를 사용할 때 `mix` 모드를 권장한다.

## LightRAG가 좋은 문제

- 여러 문서에 흩어진 개념 사이의 관계를 찾아야 하는 질문
- 특정 인물/조직/개념의 주변 맥락을 살펴야 하는 질문
- 전체 문서 컬렉션의 주제, 패턴, 흐름을 요약해야 하는 질문
- 출처와 근거 chunk를 함께 보고 싶은 RAG 시스템
- 지식 그래프 시각화가 필요한 내부 지식베이스

## 한계와 주의점

- 인덱싱 단계가 무겁다. 단순 벡터 RAG보다 LLM 호출이 많다.
- 작은 LLM은 엔티티/관계 추출 품질이 낮을 수 있다.
- embedding 모델과 차원은 처음부터 신중히 정해야 한다.
- storage backend를 문서 적재 후 바꾸는 것은 공식적으로 마이그레이션이 완전하지 않다.
- 잘못 추출된 엔티티나 중복 엔티티는 수동 병합/수정이 필요할 수 있다.
