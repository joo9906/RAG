# 05. 저장소와 운영

LightRAG는 데이터를 네 가지 storage category로 나눠 관리한다.

| Storage Type | 목적 |
|---|---|
| KV Storage | LLM cache, text chunks, 문서 정보 |
| Vector Storage | chunk/entity/relation embedding vector |
| Graph Storage | entity-relation graph |
| Doc Status Storage | 문서 처리 상태 |

## 기본 저장소

기본 설정은 로컬 파일 기반이다.

| Storage Type | 기본 구현 |
|---|---|
| KV | `JsonKVStorage` |
| Vector | `NanoVectorDBStorage` |
| Graph | `NetworkXStorage` |
| Doc Status | `JsonDocStatusStorage` |

빠른 실험에는 충분하지만, 운영에서는 데이터 규모와 동시성에 따라 외부 저장소를 고려한다.

## Server에서 저장소 선택

`.env`에 다음처럼 지정한다.

```env
LIGHTRAG_KV_STORAGE=PGKVStorage
LIGHTRAG_VECTOR_STORAGE=PGVectorStorage
LIGHTRAG_GRAPH_STORAGE=PGGraphStorage
LIGHTRAG_DOC_STATUS_STORAGE=PGDocStatusStorage
```

주의: 문서를 추가한 뒤 storage implementation을 바꾸는 마이그레이션은 공식적으로 완전 지원되지 않는다. 처음 설계할 때 신중히 정한다.

## Core에서 저장소 선택

```python
rag = LightRAG(
    working_dir="./rag_storage",
    llm_model_func=llm_model_func,
    embedding_func=embedding_func,
    kv_storage="JsonKVStorage",
    vector_storage="FaissVectorDBStorage",
    graph_storage="Neo4JStorage",
    doc_status_storage="JsonDocStatusStorage",
)
await rag.initialize_storages()
```

## Workspace

`workspace`는 여러 LightRAG 인스턴스의 데이터를 논리적으로 분리하는 이름이다.

```bash
lightrag-server --port 9621 --workspace team-a
lightrag-server --port 9622 --workspace team-b
```

저장소별 격리 방식:

| 저장소 | 격리 방식 |
|---|---|
| Json/NetworkX/NanoVectorDB/Faiss | workspace 하위 디렉터리 |
| Redis/Milvus/Mongo/PGGraph | collection/table prefix |
| Qdrant | payload filtering 기반 multitenancy |
| PGKV/PGVector/PGDocStatus | table의 `workspace` field |
| Neo4j/Memgraph | label |
| OpenSearch | index name prefix |

외부 저장소는 저장소별 workspace env가 공통 `WORKSPACE`보다 우선할 수 있다.

```env
REDIS_WORKSPACE=team-a
MILVUS_WORKSPACE=team-a
QDRANT_WORKSPACE=team-a
MONGODB_WORKSPACE=team-a
POSTGRES_WORKSPACE=team-a
NEO4J_WORKSPACE=team-a
MEMGRAPH_WORKSPACE=team-a
OPENSEARCH_WORKSPACE=team-a
```

## Neo4j

운영용 graph storage로 Neo4j를 고려할 수 있다.

```env
NEO4J_URI=neo4j://localhost:7687
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=password
NEO4J_DATABASE=neo4j
LIGHTRAG_GRAPH_STORAGE=Neo4JStorage
```

Core 예:

```python
rag = LightRAG(
    working_dir="./rag_storage",
    llm_model_func=llm_model_func,
    embedding_func=embedding_func,
    graph_storage="Neo4JStorage",
)
```

## PostgreSQL

PostgreSQL은 KV, Vector, DocStatus, Graph를 한곳에 둘 수 있는 선택지다. Graph에는 Apache AGE가 필요할 수 있다. 공식 문서는 고성능 graph 요구에서는 Neo4j가 더 낫다고 언급한다.

```env
LIGHTRAG_KV_STORAGE=PGKVStorage
LIGHTRAG_VECTOR_STORAGE=PGVectorStorage
LIGHTRAG_GRAPH_STORAGE=PGGraphStorage
LIGHTRAG_DOC_STATUS_STORAGE=PGDocStatusStorage
```

## Milvus / Qdrant / Faiss

Vector storage 규모가 커지면 전용 vector DB를 고려한다.

Milvus:

```env
MILVUS_URI=http://localhost:19530
MILVUS_DB_NAME=lightrag
LIGHTRAG_VECTOR_STORAGE=MilvusVectorDBStorage
```

Faiss는 로컬 vector index가 필요할 때 단순하다.

```bash
pip install faiss-cpu
```

```python
rag = LightRAG(
    working_dir="./rag_storage",
    llm_model_func=llm_model_func,
    embedding_func=embedding_func,
    vector_storage="FaissVectorDBStorage",
)
```

## OpenSearch

OpenSearch는 KV, Vector, Graph, DocStatus 네 종류를 모두 지원하는 통합 저장소로 쓸 수 있다.

```env
OPENSEARCH_HOSTS=localhost:9200
OPENSEARCH_USER=admin
OPENSEARCH_PASSWORD=your_password
OPENSEARCH_USE_SSL=true
OPENSEARCH_VERIFY_CERTS=false

LIGHTRAG_KV_STORAGE=OpenSearchKVStorage
LIGHTRAG_DOC_STATUS_STORAGE=OpenSearchDocStatusStorage
LIGHTRAG_GRAPH_STORAGE=OpenSearchGraphStorage
LIGHTRAG_VECTOR_STORAGE=OpenSearchVectorDBStorage
```

## 동시성 설정

문서 인덱싱 성능은 주로 LLM 처리량에 묶인다.

```env
WORKERS=2
MAX_PARALLEL_INSERT=2
MAX_ASYNC=4
```

| 설정 | 의미 |
|---|---|
| `WORKERS` | 서버 worker 수 |
| `MAX_PARALLEL_INSERT` | 동시에 처리할 파일 수 |
| `MAX_ASYNC` | 전체 LLM 동시 요청 수 |

`MAX_PARALLEL_INSERT`는 2-10 사이에서 시작하는 것이 보수적이다. 너무 높으면 엔티티 병합 충돌이 늘어날 수 있다.

## 운영 체크리스트

- embedding 모델과 dimension을 확정한 뒤 문서 인덱싱 시작
- 저장소 backend를 운영 전에 확정
- 외부 노출 시 API key와 JWT auth 모두 설정
- upload limit, streaming proxy, timeout 확인
- workspace 이름 충돌 방지
- indexing cache 사용 여부 결정
- LLM 비용 추적과 로그 보존 정책 준비
- 대량 삭제/재인덱싱 전 백업
