## 1. 핵심 기술 비교 — LightRAG vs OpenKB vs 현재 구현

### 기준별 평가표

| 기준 | 현재 구현 (05_Langgraph) | LightRAG | OpenKB |
|------|------------------------|----------|--------|
| 한국어 지원 | ✅ 완벽 | ✅ LLM 따라 결정 | ❌ 위키 영어 생성 |
| 대규모 문서 처리 | ✅ ES 클러스터 수평 확장 가능 | ⚠️ 그래프 유지비용 증가 | ❌ 인덱싱마다 LLM 비용 |
| 복합 멀티홉 추론 | ⚠️ 멀티쿼리로 일부 커버 | ✅✅ 그래프 순회 | ✅ 에이전트 목차 탐색 |
| 규제·감사 추적 | ❌ | ❌ | ❌ |
| 멀티테넌트(계열사 격리) | ❌ | ❌ | ❌ |
| 운영 성숙도 | ✅ ES/Weaviate 엔터프라이즈급 | ⚠️ 신생 프로젝트 | ⚠️ 신생 프로젝트 |
| 실시간 데이터 연동 | ✅ MCP 구조 | ❌ 정적 그래프 | ❌ 정적 위키 |
| 모순 감지 | ⚠️ 할루시네이션 검증만 | ❌ | ✅ Lint 기능 |
| 쿼리당 비용 | 중간 | 중간 | 낮음 |
| 문서 추가 비용 | 낮음 (임베딩만) | 높음 (엔티티 추출 LLM) | 높음 (위키 컴파일 LLM) |

### 결론

- **OpenKB**: 영어 위키 생성 + 멀티테넌트 없음 → 모니모 부적합
- **LightRAG**: 복합 추론 그래프 레이어로만 부분 채택
- **현재 구현**: 검색 파이프라인 기반으로 채택, 엔터프라이즈 레이어 추가 필요

## 2. 모니모급 목표 아키텍처

```
사용자 쿼리
    ↓
[Redis 시맨틱 캐시]  — 임베딩 코사인 유사도 ≥ 0.8 캐시 히트
    ↓
[동적 라우터]  — 계열사 + 도메인 분류 (멀티레벨 라우팅)
    ├─► 삼성카드 에이전트
    ├─► 삼성생명 에이전트
    ├─► 삼성증권 에이전트
    └─► 공통 금융 지식 에이전트
         ↓
    [멀티쿼리 확장]
         ↓
    ┌──────────────────────────────────┐
    │  하이브리드 검색 레이어           │
    │  Elasticsearch (BM25)            │
    │  Weaviate (Dense Vector)         │
    │  RRF 리랭킹 + Cross-Encoder      │
    └──────────────────────────────────┘
         ↓
    ┌──────────────────────────────────┐
    │  LightRAG 그래프 보강 레이어      │
    │  엔티티 추출 → 관계 탐색          │
    │  멀티홉 컨텍스트 확장             │
    └──────────────────────────────────┘
         ↓
    [답변 생성 → 할루시네이션 검증]
    [Self-correction loop (최대 2회)]
         ↓
    ┌──────────────────────────────────┐
    │  엔터프라이즈 레이어             │
    │  계열사 Vault 격리 (PostgreSQL)  │
    │  감사 로그 (이벤트 소싱)          │
    │  문서 버전 관리 (Git 기반)        │
    └──────────────────────────────────┘
```

## 3. 검색(Retrieval) 고도화 방법론

### 3-1. HyDE (Hypothetical Document Embeddings)

질문을 그대로 임베딩하는 대신, LLM이 "이 질문에 대한 이상적인 답변 문서"를 먼저 가상으로 생성하고 그것을 임베딩해서 검색하는 방식.

```
기존: "PER이 낮은 주식이 좋은가?" → 임베딩 → 검색
HyDE: "PER이 낮은 주식이 좋은가?" → LLM → 가상 답변 생성 → 임베딩 → 검색
```

짧은 구어체 질문보다 문서 스타일의 텍스트를 임베딩했을 때 코사인 유사도 정확도가 올라가는 원리를 이용한다. 현재 멀티쿼리 생성 노드 앞에 추가하면 효과적이다.

### 3-2. FLARE (Forward-Looking Active Retrieval)

답변 생성 도중 확신이 낮은 토큰이 나오는 시점을 감지해서 그 순간에만 추가 검색을 트리거하는 방식.

```
LLM 생성 중: "삼성생명 종신보험의 사망보험금 지급 기준은 [불확실]"
               → 불확실 감지 → 즉시 "사망보험금 지급 기준" 재검색
               → 검색 결과 삽입 후 생성 재개
```

현재 Self-correction은 완성 후 검증이지만 FLARE는 생성 중 실시간 검증이라 할루시네이션 발생 자체를 줄인다.

### 3-3. Adaptive RAG

모든 질문에 RAG를 쓰는 게 아니라, 먼저 LLM이 "이 질문에 검색이 필요한가"를 판단한다.

```
"PER이 뭐야?" → LLM 판단: 일반 지식, RAG 불필요 → 직접 답변 (비용↓)
"삼성생명 2026년 신상품 보장 내용은?" → 검색 필요 → RAG 실행
"오늘 코스피 지수는?" → 실시간 필요 → MCP 도구 실행
```

불필요한 벡터 검색 비용을 줄이고 응답 속도를 개선한다.

### 3-4. Contextual Compression

검색된 문서 전체를 컨텍스트에 넣지 않고, 질문과 관련된 부분만 추출·압축해서 삽입하는 방식. 토큰 절약 + 노이즈 감소.

```
검색된 약관 문서 (5,000 토큰)
   ↓ Compression LLM
질문 관련 핵심 조항만 추출 (300 토큰)
   ↓
프롬프트에 삽입
```

### 3-5. ColBERT / SPLADE 기반 Late Interaction

기존 Dense 검색은 쿼리와 문서를 각각 단일 벡터로 압축해서 비교하지만, ColBERT는 토큰 단위 다중 벡터로 세밀하게 비교한다. 금융 약관처럼 특정 키워드 하나가 의미를 바꾸는 문서에 유리하다.

```
Dense:  [쿼리 벡터] vs [문서 벡터]  → 단일 유사도 점수
ColBERT: [쿼리 토큰들] vs [문서 토큰들] → MaxSim 연산 → 더 세밀한 점수
```

### 3-6. Cross-Encoder 리랭커

현재 RRF는 점수 기반 융합이지만, Cross-Encoder는 쿼리와 문서를 쌍(pair)으로 함께 인코딩해서 더 정확한 관련성 점수를 계산한다.

```
RRF:           score(doc) = Σ 1/(rank + k)  (빠름, 덜 정확)
Cross-Encoder: score(query, doc) = BERT_CLS(concat(query, doc))  (느림, 더 정확)
```

운영 전략: RRF로 top-20 후보 선정 → Cross-Encoder로 최종 top-5 선별 (Two-stage Reranking).

## 4. 멀티에이전트 효율성 향상 방법

### 4-1. Plan-and-Execute 패턴

복잡한 질문을 먼저 하위 태스크로 분해하고 각 태스크를 병렬로 실행한다.

```
질문: "삼성생명과 삼성화재의 실손보험 보장 범위 차이를 비교하고 각각의 보험료를 알려줘"

Plan 에이전트:
  Task 1: 삼성생명 실손보험 보장 범위 검색
  Task 2: 삼성화재 실손보험 보장 범위 검색
  Task 3: 삼성생명 보험료 조회 (MCP)
  Task 4: 삼성화재 보험료 조회 (MCP)

Execute: Task 1~4 병렬 실행

Synthesize: 결과 통합 → 최종 비교 답변
```

현재 구현은 단일 쿼리 → 단일 에이전트 순서 실행이지만, Plan-and-Execute는 태스크 병렬화로 응답 지연을 크게 줄인다.

### 4-2. Reflection 패턴 (현재 Self-correction의 강화판)

현재 Self-correction은 할루시네이션 감지 시 쿼리만 수정하지만, Reflection은 에이전트가 자신의 추론 과정 전체를 비판적으로 검토한다.

```
초안 답변 생성
    ↓
Reflection 에이전트:
  - 논리적 일관성 검토
  - 답변 완전성 검토 ("질문에 모두 답했는가?")
  - 출처 신뢰도 검토
  - 개선 방향 제시
    ↓
수정 답변 생성 (반복 최대 N회)
```

### 4-3. 멀티에이전트 토론 (Debate)

동일한 질문에 대해 여러 에이전트가 독립적으로 답변하고, 판정 에이전트가 최선의 답변을 선택 또는 합성한다. 금융 상품 추천처럼 편향이 위험한 답변에 유효하다.

```
Agent A (보수적 관점): "변액보험은 원금 손실 위험이 있습니다..."
Agent B (수익 관점):   "변액보험의 기대 수익률은..."
Agent C (중립):        "투자 성향에 따라..."

Judge Agent: 세 답변 종합 → 균형 잡힌 최종 답변
```

### 4-4. Speculative Execution (투기적 실행)

라우팅 결과를 기다리지 않고 가능성이 높은 에이전트 2~3개를 미리 병렬로 실행하고, 라우팅 결과가 나오면 해당 에이전트 결과만 사용하고 나머지는 폐기한다.

```
기존: 라우팅 (200ms) → 에이전트 실행 (800ms) = 1,000ms
투기적: 라우팅 + 에이전트 2개 병렬 실행 = max(200ms, 800ms) = 800ms
```

단, LLM 비용이 증가하므로 응답 속도가 중요한 실시간 서비스에서만 적용한다.

### 4-5. LATS (Language Agent Tree Search)

Monte Carlo Tree Search를 에이전트 행동에 적용한 방법. 복잡한 금융 상담처럼 여러 단계의 추론이 필요한 경우, 각 단계에서 가능한 행동들을 트리로 탐색하고 가장 가치 있는 경로를 선택한다.

```
루트: 질문 수신
  ├─ 행동 A: RAG 검색 먼저
  │    ├─ 행동 A1: 상품 DB 조회
  │    └─ 행동 A2: 법령 DB 조회 ← (시뮬레이션 평가: 더 나음)
  └─ 행동 B: 실시간 데이터 먼저
       └─ ...
```

현재 구현처럼 단일 경로로 실행하는 것보다 복잡한 문제에서 답변 품질이 높지만, 탐색 비용이 크다.

### 4-6. 에이전트 특화 분업 (Specialization)

범용 에이전트 대신 역할이 명확히 분리된 전문 에이전트를 구성한다.

```
Orchestrator Agent
    ├─► Query Decomposer Agent    — 질문 분해
    ├─► Knowledge Retriever Agent — 문서 검색
    ├─► Data Fetcher Agent        — 실시간 데이터 (MCP)
    ├─► Reasoner Agent            — 추론·합산
    ├─► Fact Checker Agent        — 할루시네이션 검증
    └─► Response Formatter Agent  — 출력 포맷 정제
```

각 에이전트가 자신의 역할에 최적화된 시스템 프롬프트와 도구만 가지므로 오류 범위가 좁아지고 디버깅이 쉽다.

### 4-7. 에이전트 메모리 계층화

```
Sensory Memory  : 현재 대화 컨텍스트 (in-context)
Working Memory  : 현재 세션 중간 결과 (Redis TTL 짧음)
Long-term Memory: 사용자 선호·이력 요약 (Redis TTL 길거나 PostgreSQL)
Semantic Memory : 도메인 지식 (벡터 DB — Weaviate/ES)
Episodic Memory : 과거 성공/실패 Q&A 사례 (캐시 히트 이력)
```

현재 구현은 Semantic Memory(벡터 DB)와 짧은 Sensory Memory(대화 이력)만 있다. Long-term Memory를 추가하면 "지난번에 말씀하셨던 투자 성향 기준으로" 같은 개인화가 가능해진다.

## 5. 문서 인덱싱 고도화

### 5-1. Agentic Chunking (LLM 기반 청킹)

현재 `##` 헤더 단위 청킹 대신, LLM이 문서의 의미 단위를 스스로 파악해서 청크를 나눈다.

```
기존: ## 헤더 기준으로 기계적 분할
Agentic: "이 문단은 앞 문단과 같은 개념인가, 새 개념인가?"를 LLM이 판단
```

금융 약관처럼 법적 문장이 이어지는 문서에서 특히 효과적이다.

### 5-2. Late Chunking

문서를 청크로 나누기 전에 전체 문서를 임베딩 모델에 넣어 토큰 수준 표현을 얻은 뒤, 그 표현을 청크 단위로 평균 풀링해서 각 청크의 임베딩을 생성한다. 청크가 전체 문서 컨텍스트를 이해한 채로 임베딩되므로 검색 정확도가 올라간다.

### 5-3. Parent-Child Chunking

작은 청크(Child)로 검색해서 정밀도를 높이고, 실제 LLM에는 그 청크의 부모(Parent)인 큰 문단을 통째로 제공해서 문맥 손실을 막는다.

```
인덱싱: 문단(Parent) → 문장들(Child)로 분리 → Child만 벡터 저장
검색:   Child 단위로 유사도 검색 (정밀)
컨텍스트: Child의 Parent 문단 전체를 LLM에 제공 (문맥 풍부)
```

### 5-4. 문서 충돌 감지 파이프라인

모니모처럼 여러 계열사의 약관이 공존하면 동일 개념에 대해 서로 다른 기준이 존재할 수 있다.

```
신규 문서 추가 시:
  1. 기존 문서와 동일 엔티티(예: "실손보험 면책 조항") 검색
  2. 내용 비교 LLM 호출
  3. 충돌 감지 → 슬랙/이메일 알림 → 담당자 검토
  4. 해소 후 인덱싱
```

OpenKB의 Lint 개념을 자체 구현한 형태.

## 6. 인프라 및 운영 고려사항

### 6-1. 계열사별 Vault 격리

```sql
-- PostgreSQL ACL 기반 격리 (AKB 설계 참고)
-- 각 계열사는 별도 스키마 + 역할
CREATE SCHEMA samsung_card;
CREATE SCHEMA samsung_life;

CREATE ROLE akb_samsung_card_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA samsung_card TO akb_samsung_card_reader;
-- samsung_card_reader는 samsung_life 스키마에 접근 불가
```

AI 에이전트가 삼성카드 질문에 삼성생명 약관을 가져오는 사고를 DB 레벨에서 차단한다.

### 6-2. 감사 추적 (Audit Trail)

금융 서비스는 "이 AI가 왜 이 답변을 했는가"를 규제 당국에 설명해야 할 수 있다.

```
모든 쿼리 → 검색된 문서 → 생성된 답변 → 할루시네이션 판정
이 전체 체인을 불변 로그로 저장 (Append-only PostgreSQL or Kafka)
```

### 6-3. Shadow Mode 배포

새 파이프라인(예: LightRAG 그래프 레이어 추가)을 실제 서비스에 바로 반영하지 않고, 기존 파이프라인과 병렬로 실행하면서 답변 품질을 오프라인에서 비교한다.

```
사용자 쿼리 → 기존 파이프라인 → 실제 응답 (사용자에게 전달)
            └─ 신규 파이프라인 → Shadow 응답 (로그만 저장, 사용자 미전달)

일정 기간 후 품질 메트릭 비교 → 신규로 전환 여부 결정
```

### 6-4. 비용 제어

```
계층별 캐시 전략:
  L1: Redis 시맨틱 캐시 (유사도 ≥ 0.8, 24h TTL)   → 가장 저렴
  L2: 결과 캐시 (정확히 동일 쿼리, 1h TTL)          → 저렴
  L3: 임베딩 캐시 (동일 문서 재임베딩 방지)          → 중간
  L4: LLM 응답 캐시 (동일 컨텍스트+쿼리)            → 고가이나 효과 큼

토큰 예산 관리:
  - Haiku: 간단한 분류/라우팅
  - Sonnet: 일반 검색·답변
  - Opus: 복잡한 멀티홉 추론·할루시네이션 판정
```

### 6-5. 스트리밍 응답

모니모 앱에서 답변이 완전히 생성될 때까지 기다리면 UX가 나쁘다. LangGraph의 스트리밍 + SSE(Server-Sent Events)로 토큰 단위로 점진적으로 전달한다.

```python
async for chunk in graph.astream({"messages": [...]}, stream_mode="values"):
    yield f"data: {chunk}\n\n"
```

## 7. 금융 도메인 특화 고려사항

### 7-1. 한국어 특화 임베딩

현재 `text-embedding-3-small`은 영어 중심이다. 금융 특화 한국어 임베딩 옵션:

| 모델 | 특징 |
|------|------|
| `ko-sroberta-multitask` | 한국어 STS 특화, 무료 |
| `bge-m3` | 다국어, OpenKB 벤치마크 사용 모델 |
| OpenAI `text-embedding-3-large` | 고성능, 유료 |
| 사내 Fine-tuned 모델 | 금융 도메인 용어 최적화 (이상적) |

### 7-2. 금융 용어 동의어 사전

"PER", "주가수익비율", "Price-to-Earnings Ratio"는 같은 개념이지만 벡터 검색에서 거리가 멀 수 있다.

```python
FINANCIAL_SYNONYMS = {
    "PER": ["주가수익비율", "P/E", "Price-to-Earnings"],
    "실손보험": ["실손의료보험", "실비보험", "의료실비"],
    "ETF": ["상장지수펀드", "인덱스 ETF"],
}
# 쿼리 확장 시 동의어도 함께 검색
```

### 7-3. 규제 준수 필터

AI가 금융 상품 추천을 하면 자본시장법 위반이 될 수 있다. 답변 후처리 단계에서 규제 키워드를 감지해 면책 문구를 자동 삽입한다.

```
답변에 "추천", "매수", "투자하세요" 등이 포함되면:
→ "본 정보는 투자 권유가 아닌 정보 제공 목적입니다. 투자 결정은 본인 판단으로 하세요." 자동 추가
```

### 7-4. 개인정보 마스킹

사용자 쿼리에 주민등록번호, 계좌번호, 카드번호 등이 포함될 경우 LLM에 전달하기 전에 마스킹한다.

```python
import re
PII_PATTERNS = {
    "주민번호": r"\d{6}-[1-4]\d{6}",
    "카드번호": r"\d{4}-\d{4}-\d{4}-\d{4}",
    "계좌번호": r"\d{3}-\d{2,3}-\d{6,7}",
}
```

## 8. 도입 로드맵 (단계별)

### Phase 1 — 현재 구현 엔터프라이즈화 (1~3개월)

- [ ] 계열사별 ES 인덱스 격리 + PostgreSQL ACL
- [ ] 감사 로그 파이프라인 (Kafka or PostgreSQL Append-only)
- [ ] 개인정보 마스킹 미들웨어
- [ ] 규제 준수 후처리 필터
- [ ] 비용 제어 캐시 계층화

### Phase 2 — 검색 품질 고도화 (3~6개월)

- [ ] HyDE 도입 (멀티쿼리 확장 전 단계)
- [ ] Cross-Encoder Two-stage Reranking (RRF → Cross-Encoder)
- [ ] Parent-Child Chunking 전환
- [ ] 한국어 특화 임베딩 모델 교체 또는 Fine-tuning
- [ ] 금융 동의어 사전 구축

### Phase 3 — 그래프 레이어 추가 (6~12개월)

- [ ] LightRAG 그래프 레이어 Shadow Mode 실험
- [ ] 금융 엔티티·관계 온톨로지 설계 (약관 ↔ 법령 ↔ 상품)
- [ ] 멀티홉 추론 A/B 테스트
- [ ] 문서 충돌 감지 파이프라인

### Phase 4 — 멀티에이전트 고도화 (12개월+)

- [ ] Plan-and-Execute 오케스트레이터
- [ ] 에이전트 특화 분업 구조
- [ ] 멀티에이전트 메모리 계층화 (Long-term Memory)
- [ ] FLARE 기반 실시간 검색 보강
- [ ] Adaptive RAG (검색 필요성 판단)
