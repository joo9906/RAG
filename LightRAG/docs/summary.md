## 1. 개요

`total_process.py`는 `process.py`(삽입·쿼리 파이프라인)와 `entity_solution.py`(고립 노드 해소 유틸리티)를 **하나의 파일로 통합**하고, 두 파일에는 없던 고도화 기능을 추가한 통합 파이프라인입니다.

### 핵심 기능 한눈에 보기

| 기능          | 설명                                                               |
| ------------- | ------------------------------------------------------------------ |
| **삽입**      | MD 파일 → LightRAG 삽입, 파일별 LLM/EMB 토큰·비용·시간 상세 출력   |
| **힐링**      | 고립 노드(degree=0) 자동 감지 → 4전략으로 자동 해소 → GraphML 저장 |
| **시각화**    | pyvis 기반 인터랙티브 knowledge_graph.html 생성                    |
| **통계**      | 노드·엣지·타입 분포·고립률·연결도 분석                             |
| **쿼리**      | 단건 / 4종 모드 비교 / 배치                                        |
| **쿼리 캐시** | 임베딩 코사인 유사도 기반 응답 재사용 (비용 절감)                  |
| **비용 추적** | 삽입 / 힐링 / 쿼리 3개 phase 독립 집계, 최종 요약 출력             |

## 2. 파일 구조 및 아키텍처

```
total_process.py
│
├── CONFIG (상단 블록) ─────────────────────────────────────────
│     [1] 데이터 경로 (WORKING_DIR, MD_DIR, QDRANT)
│     [2] LLM 모델 + 단가 테이블
│     [3] 임베딩 모델 (EMB_MODEL, EMB_DIM)
│     [4] 청크 설정 (CHUNK_SIZE, CHUNK_OVERLAP)
│     [5] 쿼리 캐시 임계값
│     [6] 힐링 기본값 (전략별 임계값·제한 수)
│
├── 공통 유틸 ─────────────────────────────────────────────────
│     _count()          # 토큰 카운트 (tiktoken)
│     _cost()           # 비용 계산 (LLM + EMB 단가)
│     _raw_embed()      # OpenAI 임베딩 직접 호출 (dimensions 지원)
│     _cosine_sim()     # 코사인 유사도
│
├── LightRAG 래퍼 ──────────────────────────────────────────────
│     tracked_llm()     # LLM 호출 + 토큰/비용/시간 추적
│     tracked_embed()   # 임베딩 호출 + 추적
│     _build_rag()      # LightRAG 인스턴스 생성 (Qdrant 연동)
│
├── [1] 삽입 파이프라인 ─────────────────────────────────────────
│     insert_documents()
│     print_insert_summary()
│
├── [2] 힐링(노드 개선) 파이프라인 ─────────────────────────────────────────
│     _strategy_prune()   # 전략 A
│     _strategy_embed()   # 전략 B
│     _strategy_llm()     # 전략 C
│     _strategy_relink()  # 전략 D
│     run_heal()          # 전략 조합 실행 + 저장
│     print_heal_cost()
│
├── [3] 그래프 통계 ─────────────────────────────────────────────
│     print_graph_stats()
│     print_isolated_detail()
│
├── [4] 시각화 ─────────────────────────────────────────────────
│     visualize_graph()
│
├── [5] 쿼리 파이프라인 ─────────────────────────────────────────
│     QueryCache            # 쿼리 캐시 클래스
│     _run_one_query()      # 단건 실행 (캐시→실행→출처→저장)
│     run_queries()         # 기본 쿼리 목록 순차 실행
│     run_mode_compare()    # 4종 모드 동시 비교
│     run_batch_queries()   # 파일 기반 배치 실행
│
└── main() + _build_parser() ──────────────────────────────────
      CLI argparse + 전체 파이프라인 진입점
```

### 비용 추적 구조

```python
_usage = {
    "insert": {"llm_in": 0, "llm_out": 0, "emb": 0},
    "query":  {"llm_in": 0, "llm_out": 0, "emb": 0},
    "heal":   {"llm_in": 0, "llm_out": 0, "emb": 0},  # ← 신규 추가
}
```

삽입·힐링·쿼리를 독립 phase로 분리하여 각 단계의 비용을 명확하게 구분합니다.  
힐링 전략 B(임베딩)와 C/D(LLM)에서 발생하는 API 호출은 `heal` phase에 집계됩니다.

## 3. CONFIG 설정 가이드

파일 상단의 CONFIG 블록만 수정하면 전체 동작이 바뀝니다.

```python
# [1] 데이터 경로
ENV_JSON_PATH     = "../.env.json"          # {"openai_api_key": "sk-..."}
WORKING_DIR       = "./lightrag_before_chunk_test"
MD_DIR            = "../test_md"
QDRANT_URL        = "http://localhost:6333"
QDRANT_COLLECTION = "lightrag_before_chunk_test"

# [2] LLM
LLM_MODEL = "mini"    # "mini" = gpt-4o-mini ($0.15/1M in, $0.60/1M out)
                      # "4o"   = gpt-4o      ($2.50/1M in, $10.00/1M out)

# [3] 임베딩
EMB_MODEL = "text-embedding-3-large"
EMB_DIM   = 2048      # Qdrant 컬렉션 차원과 반드시 일치

# [4] 청크
CHUNK_SIZE    = 1000  # 토큰 (작을수록 세밀, 비용 증가)
CHUNK_OVERLAP = 150   # 이전 청크와 겹치는 토큰 (컨텍스트 유지)
만약 커스터마이징 청크를 활용할 경우 청크 부분은 제거.

# [5] 쿼리 캐시
CACHE_SIMILARITY_THRESHOLD = 0.85
# 이 이상이면 캐시 히트. 기존에는 0.6 수준으로 매우 낮았는데 0.85로 상향 조정. 테스트를 여러번 거치며 임계값의 조정 필요

# [6] 힐링
HEAL_EMBED_THRESHOLD = 0.75   # 전략 B: 임베딩 유사도 최소값
HEAL_LLM_LIMIT       = 50     # 전략 C: LLM 처리 최대 노드 수
```

## 4. 파이프라인 단계별 설명

### 전체 파이프라인 흐름 (옵션 없이 실행 시)

```
python total_process.py
```

```
[삽입] MD 파일 전체 → LightRAG ainsert()
   ↓ LLM·EMB 토큰·비용·시간 파일별 상세 출력
[힐링] 고립 노드 자동 감지 → 전략 A+B+C 순서 실행
   ↓ GraphML 백업 후 저장
[시각화] knowledge_graph.html 생성
[통계]  최종 그래프 분석 출력
[쿼리]  DEFAULT_QUERIES 4개 순차 실행 + 캐시 저장
[요약]  삽입/힐링/쿼리 단계별 비용 최종 출력
```

### [1] 삽입 파이프라인

- `MD_DIR` 안의 `.md` 파일을 이름 순서대로 처리
- 각 파일마다 `_file_log`를 초기화하여 **파일 단위 비용** 집계
- `entity_extract_max_gleaning=2`: 엔티티 재추출 2회 (기본값 1보다 높음, 누락 방지)
- `force_llm_summary_on_merge=3`: 3개 이상 중복 설명 시 LLM 요약 발동 (기본값 8보다 낮음)
- `language="Korean"`: 한국어 문서 추출 정확도 향상

### [2] 힐링 파이프라인

> 별도 섹션 5에서 상세 설명

### [3] 그래프 통계

출력 항목:

- 노드·엣지 수
- 연결 컴포넌트 수 + **고립 노드 수 (%)** ← 비율 추가
- 평균/최대 연결도
- 엔티티 타입별 분포
- 연결도 상위 10 엔티티

### [4] 시각화 (pyvis)

- 노드 크기 = `degree × 3` (연결도 반영)
- 엔티티 타입별 색상 자동 배정 (팔레트 10종)
- 물리 시뮬레이션: Barnes-Hut 알고리즘 (`gravitationalConstant=-8000`)
- 노드 1,000개 초과 시 연결도 상위만 표시 (`--max-nodes` 조정 가능)
- 범례(Entity Types) 우측 상단 고정

### [5] 쿼리 파이프라인

쿼리 실행 순서:

```
1) 쿼리 임베딩 생성
2) 캐시 조회 (코사인 유사도 ≥ threshold → 캐시 히트)
3) LightRAG aquery() 실행 (mode: hybrid/local/global/naive)
4) 타이밍 분석 (임베딩·서칭·검색보조LLM·답변생성LLM)
5) 출처 엔티티 추출 (프롬프트 패턴 매칭)
6) 캐시 저장
```

쿼리 캐시는 임베딩 차원 불일치 시 자동으로 `.dim{N}.bak`으로 백업 후 초기화합니다.

## 5. 고립 노드 힐링 — 4가지 전략 상세

그래프에서 **degree=0인 노드(고립 노드)**는 검색 시 활용되지 않으며 그래프 품질을 저하시킵니다. 4가지 전략으로 단계적으로 해소합니다.

### 전략 A — Prune (삭제)

```python
# 삭제 기준 (OR 조건)
① 설명(description)이 완전히 비어있는 노드
② entity_type == "UNKNOWN"  AND  설명 길이 < min_desc_len (기본 10자)
```

- LightRAG가 엣지 처리 중 자동 생성하는 `entity_type="UNKNOWN"` 노드가 주 대상
- API 호출 없음, 즉시 실행
- 이번 실행에서는 모든 고립 노드가 설명을 갖고 있어 **0개 삭제**

### 전략 B — Embed (임베딩 유사도 연결)

```
고립 노드 N개 + 연결된 노드 M개
  → (이름 + 설명) 텍스트를 임베딩
  → 코사인 유사도 계산 (N × M)
  → 유사도 ≥ threshold인 쌍에 엣지 추가 (최대 top_k개/노드)
```

| 파라미터    | 기본값 | 설명                         |
| ----------- | ------ | ---------------------------- |
| `threshold` | 0.75   | 연결할 최소 코사인 유사도    |
| `top_k`     | 2      | 고립 노드 1개당 최대 연결 수 |

추가되는 엣지 속성:

```
relation_name: "semantic_similarity"
weight: <코사인 유사도값>
description: "임베딩 유사도 기반 자동 연결 (cosine=0.XXXX)"
```

### 전략 C — LLM (관계 제안)

```
연결도 상위 N개 노드를 후보로 제시
  → 고립 노드 10개씩 배치로 LLM에 전달
  → LLM이 각 고립 노드와 관련 있는 후보를 JSON으로 반환
  → confidence ≥ min_confidence인 제안만 엣지로 삽입
```

LLM에게 전달하는 정보:

```
[고립 노드]
  id=xxx  name=경기도 성남시 분당구...  type=위치  desc=...
[후보 노드]
  id=yyy  name=수벡스정  type=제품  desc=편두통 치료제...
  ...
```

LLM 응답 형식:

```json
[
  {
    "isolated_id": "xxx",
    "candidate_id": "yyy",
    "relation": "판매 장소",
    "description": "해당 주소에서 수벡스정 판매",
    "confidence": 0.9
  }
]
```

### 전략 D — Re-link (소스 청크 재추출)

```
고립 노드의 source_id 필드로 원본 청크 텍스트 복원
  → LLM에게 "이 텍스트에서 [타겟 엔티티]와 관련된 관계를 추출해줘" 요청
  → 기존 노드와 이름 매칭하여 엣지 삽입
```

- 기본적으로 비활성화 (`--heal-all` 또는 `--heal-relink`로 명시 실행)
- KV 스토어 JSON 파일이 없으면 자동 스킵

### 전략 실행 순서 및 기본 조합

| 실행 방식                                   | A   | B   | C   | D   |
| ------------------------------------------- | --- | --- | --- | --- |
| `python total_process.py` (전체 파이프라인) | ✓   | ✓   | ✓   | -   |
| `--heal`                                    | ✓   | ✓   | ✓   | -   |
| `--heal --heal-all`                         | ✓   | ✓   | ✓   | ✓   |
| `--heal-prune`                              | ✓   | -   | -   | -   |
| `--heal-embed`                              | -   | ✓   | -   | -   |
| `--heal-llm`                                | -   | -   | ✓   | -   |
| `--heal-relink`                             | -   | -   | -   | ✓   |

> **안전성**: 모든 전략 실행 전 GraphML 파일이 `.bak_YYYYMMDD_HHMMSS` 형태로 자동 백업됩니다.

## 6. CLI 사용법

### 전체 파이프라인

```bash
# 삽입 → 힐링(A+B+C) → 시각화 → 통계 → 기본 쿼리
python total_process.py

# 삽입 생략
python total_process.py --skip-insert

# 전략 D(Re-link)까지 포함
python total_process.py --heal-all
```

### 힐링 단독

```bash
# 기본 (A+B+C)
python total_process.py --heal

# 전략 선택
python total_process.py --heal-prune                # A만
python total_process.py --heal-embed                # B만
python total_process.py --heal-llm                  # C만
python total_process.py --heal --heal-all           # A+B+C+D

# 변경 전 미리보기 (저장 안 함)
python total_process.py --heal --dry-run

# 고립 노드 상세 목록 출력 후 힐링
python total_process.py --heal --isolated-detail

# 파라미터 조정
python total_process.py --heal \
  --embed-threshold 0.80 \
  --embed-top-k 3 \
  --llm-limit 100 \
  --llm-min-confidence 0.6
```

### 쿼리

```bash
# 단건 쿼리
python total_process.py -q 기넥신 효능이 뭐야?

# 쿼리 모드 지정
python total_process.py -q 기넥신 효능은? --mode local

# 4종 모드 비교 (naive/local/global/hybrid)
python total_process.py --mode-compare 류마티스 관절염 치료제 추천

# 배치 쿼리 (질문 파일 → batch_result.md 저장)
python total_process.py --batch questions.txt
```

### 통계 / 시각화

```bash
# 그래프 통계만
python total_process.py --stats

# 시각화만
python total_process.py --visualize

# 노드 수 제한 조정
python total_process.py --visualize --max-nodes 500
```

### 캐시 관련

```bash
# 캐시 내용 조회
python total_process.py --show-cache

# 캐시 비활성화
python total_process.py -q 질문 --no-cache

# 캐시 유사도 임계값 조정
python total_process.py -q 질문 --cache-threshold 0.85
```

### 모델 / 청크 설정 오버라이드

```bash
# 고품질 모델로 실행
python total_process.py --llm 4o

# 청크 크기 조정
python total_process.py --chunk-size 800 --chunk-overlap 100
```

## 10. 남은 한계와 개선 방향

### 현재 한계

**고립 노드 162개 잔존 (21.3%)의 원인:**

1. **엔티티 타입 혼재 (한/영)**: `concept`과 `개념`, `person`과 `사람`이 별도 타입으로 존재. LLM이 동일 개념을 다른 언어로 추출하여 연결 기회를 놓침
2. **맥락 부재 엔티티**: 단일 청크에서만 등장하고 다른 청크와 연결될 문맥이 없는 엔티티 (예: 상병코드, 특정 주소)
3. **전략 B 임계값**: 0.75 이하 유사도 쌍은 연결하지 않음 — 낮추면 노이즈 증가 가능성
4. **전략 C LLM 한계**: confidence 기반 필터링으로 관계가 불명확한 노드는 제안하지 않음 (→ 정확도는 높지만 해소 범위 제한)
5. **Qdrant 미갱신**: 힐링은 GraphML만 수정하며 Qdrant 벡터 스토어는 갱신하지 않음 (새로 추가된 엣지는 벡터 검색에 미반영)

### 개선 방향

1. **엔티티 타입 정규화**: 삽입 후 한/영 혼재 타입을 통합하는 후처리 단계 추가 (`개념→concept`, `사람→person` 등)
2. **임계값 단계적 완화**: 전략 B를 0.75 → 0.70 → 0.65로 단계 실행하는 cascade 모드
3. **전략 C 후보 다양화**: 연결도 상위만 제시하지 않고, **같은 소스 문서 출신 노드**를 우선 후보로 제시
4. **전략 D 활성화 검토**: 소스 청크가 있는 고립 노드에 Re-link를 적용하면 추가 해소 가능 (비용 증가와 트레이드오프)
5. **삽입 파라미터 조정**: `CHUNK_SIZE` 축소 (1000 → 600) 또는 `entity_extract_max_gleaning` 증가로 관계 추출 정밀도 향상
6. **Qdrant 동기화**: 힐링으로 추가된 엣지를 LightRAG KV 스토어에도 반영하는 로직 추가
