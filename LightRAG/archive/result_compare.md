## 3. 항목별 분석

### 엔티티 조회

- **A 방식**: 딕셔너리 O(1) 해시 탐색
- **B 방식**: B-tree 인덱스 O(log n) 탐색 + 네트워크 왕복
- **해석**: 그래프가 인메모리에 있으면 A가 유리하나, 규모가 커지면 메모리 부족으로 A 자체가 불가능해진다.

### 타입 필터

- **A 방식**: 전체 노드 선형 스캔 O(n)
- **B 방식**: entity_type 인덱스 스캔 O(k)
- **해석**: 엔티티 수가 많을수록 B의 인덱스 효과가 극대화된다. 수만 노드 이상에서 역전이 뚜렷해진다.

### 1홉 탐색

- **A 방식**: adjacency list 직접 접근 O(degree)
- **B 방식**: source_entity 인덱스 JOIN O(log n + degree)
- **해석**: 인메모리라 A가 절대적으로 빠르다. 단, 그래프 로딩(수십초) 비용은 B에 없다.

### 2홉 탐색

- **A 방식**: BFS deque — O(V+E) 범위 내
- **B 방식**: 재귀 CTE — 인덱스 기반 레벨별 JOIN
- **해석**: 현재 규모(567 노드)에서는 A가 빠르다. 수만 노드 이상이면 인메모리 BFS가 메모리 한계에 걸린다.

### 청크 조회

- **A 방식**: 딕셔너리 O(1) 해시
- **B 방식**: PK 인덱스 O(log n)
- **해석**: 단순 조회는 인메모리 A가 항상 빠르다. 단, 대용량에서는 RAM 부족으로 A 사용 불가.

### 청크→엔티티

- **A 방식**: 사전 구성된 역인덱스 dict O(1)
- **B 방식**: GIN 인덱스 없이 ANY(array) 스캔
- **해석**: GIN 인덱스를 추가하면 B가 대용량에서 A보다 빠를 수 있다. 현재는 인메모리 역인덱스 A가 유리.

### 전체 파이프라인

- **A 방식**: 엔티티 조회 + 1홉 + 청크 수집 (모두 인메모리)
- **B 방식**: 3개 쿼리 순차 실행 (각각 네트워크 왕복)
- **해석**: 단일 사용자 기준 A가 빠르다. 동시 요청 N명 시 A는 메모리 N배 필요, B는 커넥션 풀로 공유.

## 분석

### 처리량 차이가 발생하는 이유

**A (NetworkX)**
- 모든 스레드가 하나의 인메모리 그래프를 공유하므로 I/O가 없음
- 단, Python GIL로 인해 CPU 바운드 구간은 진정한 병렬 실행이 아님
- 스레드 수가 늘어도 메모리 사용량은 그래프 1개 분량으로 고정됨

**B (PostgreSQL)**
- 각 요청마다 TCP 소켓 통신 + DB 내부 잠금 처리 발생
- 커넥션 풀(최대 {CONCURRENT_USERS}개)로 연결 생성 오버헤드는 최소화
- DB 자체가 진정한 병렬 처리: 여러 쿼리를 동시에 실행
